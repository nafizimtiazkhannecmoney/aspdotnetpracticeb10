1. Why Serilog instead of the default logger?

  • Structured logging – you can log objects and properties, not just plain text
  • Multiple sinks at the same time (File + Console + Seq + Elasticsearch…)
  • Rolling files with automatic cleanup
  • Beautiful output templates
  • Configuration entirely in appsettings.json (no hard-coded paths)
  • Works perfectly with ILogger<T> dependency injection

2. Installation

dotnet add package Serilog.AspNetCore
dotnet add package Serilog.Sinks.File

# Optional but highly recommended
dotnet add package Serilog.Sinks.Console
dotnet add package Serilog.Enrichers.Environment
dotnet add package Serilog.Enrichers.Thread
dotnet add package Serilog.Expressions          # for advanced filtering

3. Minimal Working Configuration

This is the smallest configuration that actually works and writes to a file:

{
  "Serilog": {
    "Using": [ "Serilog.Sinks.File" ],
    "MinimumLevel": "Information",
    "WriteTo": [
      {
        "Name": "File",
        "Args": {
          "path": "Logs/myapp-.log",
          "rollingInterval": "Day"
        }
      }
    ]
  }
}
Relative path Logs/myapp-.log creates a folder next to your executable. Prefer this over absolute paths (C:/Logs/...) when possible.

4. MinimumLevel – Full Control Over What Gets Logged

This is one of the most powerful sections.

"MinimumLevel": {
  "Default": "Information",
  "Override": {
    "Microsoft": "Warning",
    "Microsoft.AspNetCore": "Warning",
    "Microsoft.EntityFrameworkCore": "Warning",
    "System": "Warning",
    "YourNamespace.Controllers": "Debug",
    "YourNamespace.Services.PaymentService": "Verbose"
  }
}

Available Levels (from lowest to highest)

Level When to use Typical use case
Verbose Extremely detailed Debugging complex algorithms, very rare in production
Debug Development details Variable values, flow control
Information Recommended default Business events, important actions
Warning Something unexpected but recoverable Retry, fallback, deprecated usage
Error Something failed Exceptions, failed operations
Fatal Application is about to die Unrecoverable errors, startup failures
Pro tip: Keep Default at Information in production. Use Override to silence noisy Microsoft packages and to raise the level only for the namespaces you care about.

5. WriteTo – All Useful Options Explained

5.1 File Sink (most important)

{
  "Name": "File",
  "Args": {
    "path": "Logs/myapp-.log",
    "rollingInterval": "Day",
    "retainedFileCountLimit": 31,
    "fileSizeLimitBytes": 10485760,
    "rollOnFileSizeLimit": true,
    "shared": false,
    "flushToDiskInterval": "00:00:01",
    "outputTemplate": "{Timestamp:yyyy-MM-dd HH:mm:ss.fff zzz} [{Level:u3}] ({SourceContext}) {Message:lj}{NewLine}{Exception}",
    "restrictedToMinimumLevel": "Information"
  }
}
Option What it does Recommended value
path Where the log file is written. The - is replaced by the date when using rolling. Logs/myapp-.log
rollingInterval How often a new file is created.
Possible values: Infinite, Year, Month, Day, Hour, Minute		 Day
retainedFileCountLimit How many old log files to keep. Older ones are deleted automatically. 14 or 31
fileSizeLimitBytes Maximum size of a single file (in bytes). 10 MB = 10485760 10485760 (10 MB)
rollOnFileSizeLimit If true, creates a new file when size limit is reached (even before the interval). true
shared Allows multiple processes to write to the same file (slightly slower). false (unless you need it)
flushToDiskInterval How often logs are forced to disk. Prevents loss on crash. "00:00:01" (every second)
outputTemplate The exact format of each log line (see section below). See recommended template
restrictedToMinimumLevel This sink only receives logs of this level or higher (overrides global MinimumLevel). Usually leave empty

5.2 Recommended Output Template

"{Timestamp:yyyy-MM-dd HH:mm:ss.fff zzz} [{Level:u3}] ({SourceContext}) {Message:lj}{NewLine}{Exception}"
Token Meaning
{Timestamp:yyyy-MM-dd HH:mm:ss.fff zzz} Date + time with milliseconds + timezone
[{Level:u3}] Level in 3 uppercase letters: INF, WRN, ERR, FTL…
({SourceContext}) The class name that logged the message (very useful!)
{Message:lj} The actual message. lj = literal + JSON-friendly
{NewLine}{Exception} Puts the full exception on the next lines

5.3 Console Sink (great for development)

{
  "Name": "Console",
  "Args": {
    "outputTemplate": "[{Timestamp:HH:mm:ss} {Level:u3}] {Message:lj}{NewLine}{Exception}",
    "theme": "Serilog.Sinks.SystemConsole.Themes.AnsiConsoleTheme::Code, Serilog.Sinks.Console"
  }
}
The theme makes the console colorful (green for Information, yellow for Warning, red for Error).

5.4 Multiple Sinks at the same time

"WriteTo": [
  { "Name": "Console" },
  {
    "Name": "File",
    "Args": {
      "path": "Logs/myapp-.log",
      "rollingInterval": "Day",
      "retainedFileCountLimit": 31,
      "outputTemplate": "{Timestamp:yyyy-MM-dd HH:mm:ss.fff} [{Level:u3}] ({SourceContext}) {Message:lj}{NewLine}{Exception}"
    }
  }
]

6. Enrich – Add Extra Context Automatically

Enrichers add properties to every log event without you writing extra code.

"Enrich": [
  "FromLogContext",
  "WithMachineName",
  "WithThreadId",
  "WithEnvironmentName",
  "WithEnvironmentUserName"
]
Enricher What it adds Package needed
FromLogContext Properties you push with LogContext.PushProperty Built-in
WithMachineName Computer / container name Serilog.Enrichers.Environment
WithThreadId Current thread ID Serilog.Enrichers.Thread
WithEnvironmentName Development / Staging / Production Serilog.Enrichers.Environment
WithEnvironmentUserName Windows / Linux username running the app Serilog.Enrichers.Environment
After adding enrichers, you can include them in the output template:
{MachineName} | {ThreadId} | {EnvironmentName}

7. Filter – Advanced Control (Optional)

You can exclude certain logs completely.

"Filter": [
  {
    "Name": "ByExcluding",
    "Args": {
      "expression": "RequestPath like '/health%'"
    }
  }
]

This requires the package Serilog.Expressions.

Filtering is powerful but can hide important information. Use it carefully.

8. Complete Production-Ready Program.cs

using Serilog;

Log.Logger = new LoggerConfiguration()
    .ReadFrom.Configuration(new ConfigurationBuilder()
        .AddJsonFile("appsettings.json")
        .AddJsonFile($"appsettings.{Environment.GetEnvironmentVariable("ASPNETCORE_ENVIRONMENT") ?? "Production"}.json", true)
        .Build())
    .Enrich.FromLogContext()
    .CreateLogger();

try
{
    Log.Information("=== Application Starting ===");

    var builder = WebApplication.CreateBuilder(args);

    // This is the magic line
    builder.Host.UseSerilog();

    // Your services
    builder.Services.AddControllers();
    // builder.Services.AddDbContext... etc.

    var app = builder.Build();

    // Logs every HTTP request automatically
    app.UseSerilogRequestLogging(options =>
    {
        options.MessageTemplate = "HTTP {RequestMethod} {RequestPath} responded {StatusCode} in {Elapsed:0.0000} ms";
    });

    // app.UseAuthentication();
    // app.UseAuthorization();

    app.MapControllers();

    app.Run();
}
catch (Exception ex)
{
    Log.Fatal(ex, "Application terminated unexpectedly");
}
finally
{
    Log.CloseAndFlush();
}

9. How to Log Correctly in Your Code

Best practice – Constructor injection

public class OrderService
{
    private readonly ILogger<OrderService> _logger;

    public OrderService(ILogger<OrderService> logger)
    {
        _logger = logger;
    }

    public async Task CreateOrder(Order order)
    {
        _logger.LogInformation("Creating order for customer {CustomerId} with total {Total}",
            order.CustomerId, order.Total);

        try
        {
            // ... business logic
            _logger.LogInformation("Order {OrderId} created successfully", order.Id);
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "Failed to create order for customer {CustomerId}", order.CustomerId);
            throw;
        }
    }
}
Important: Always use message templates with {PropertyName} instead of string interpolation.
Good → _logger.LogInformation("User {UserId} logged in", userId);
Bad → _logger.LogInformation($"User {userId} logged in");

10. Final Checklist

  1. ☐ Install Serilog.AspNetCore + Serilog.Sinks.File (+ Console if wanted)
  2. ☐ Create a rich "Serilog" section in appsettings.json
  3. ☐ Configure MinimumLevel + useful Overrides
  4. ☐ Configure File sink with rollingInterval, retainedFileCountLimit, good outputTemplate
  5. ☐ (Optional) Add enrichers
  6. ☐ Create bootstrap logger at the very top of Program.cs
  7. ☐ Call builder.Host.UseSerilog()
  8. ☐ Call app.UseSerilogRequestLogging()
  9. ☐ Wrap host in try / catch / finally + Log.CloseAndFlush()
  10. ☐ Inject ILogger<T> everywhere and use structured logging
You now have a production-grade logging setup.
