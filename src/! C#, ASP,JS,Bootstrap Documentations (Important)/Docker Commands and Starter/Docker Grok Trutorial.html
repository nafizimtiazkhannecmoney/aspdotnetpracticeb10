1. Do I need to build the project first?

No. You do not need to run dotnet build or dotnet publish on your machine first. Docker will build and publish the application inside the image using a multi-stage Dockerfile. The final image only contains the published app + the ASP.NET Core runtime – it is small and ready to run.

2. Prerequisites

  • An ASP.NET Core 8.0 project
  • Docker Desktop installed and running (Windows / macOS)
  • Prefer Linux containers mode (the default and recommended for ASP.NET Core)
You can do the entire process with Docker Desktop (GUI + terminal). No extra tools are required.

3. Create the Dockerfile

Create a file named exactly Dockerfile (no extension) next to your .csproj file.

Important: The file must be named Dockerfile (not Dockerfile.txt). If Windows adds a .txt extension, rename it and remove the extension.

Final working Dockerfile (includes the fixes we applied later):

# Build stage
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src

# Copy csproj first for better layer caching
COPY ["NecSanctionScreening.csproj", "."]
RUN dotnet restore "NecSanctionScreening.csproj"

# Copy the rest of the source
COPY . .
RUN dotnet publish "NecSanctionScreening.csproj" -c Release -o /app/publish /p:UseAppHost=false

# Runtime stage (smaller image)
FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS final
WORKDIR /app
EXPOSE 8080

# Create logs directory so the app can write log files
RUN mkdir -p /app/logs

# Hardcode the environment (so the app always runs in the correct mode inside the container)
ENV ASPNETCORE_ENVIRONMENT=Production
ENV ASPNETCORE_URLS=http://+:8080

# Copy only the published output
COPY --from=build /app/publish .

ENTRYPOINT ["dotnet", "NecSanctionScreening.dll"]

Replace NecSanctionScreening with the real name of your project (the name of the .csproj / .dll).

Why multi-stage?

  • The first stage uses the large SDK image to restore, build and publish.
  • The second stage uses the small runtime image and only copies the published files.
  • Result: a much smaller final image that is safe to share.

4. Create the .dockerignore file

Create a file named .dockerignore in the same folder as the Dockerfile. This prevents unnecessary files from being sent to Docker and keeps the build faster and cleaner. 

**/.git
**/.vs
**/bin
**/obj
**/node_modules
**/*.user
**/*.suo
**/Dockerfile*
**/.dockerignore

5. Build the Docker image

1 Make sure Docker Desktop is running.
2 Open a terminal (PowerShell, Command Prompt, or the integrated terminal in Visual Studio / VS Code).
3 Navigate to the folder that contains the .csproj, Dockerfile and .dockerignore: 

cd "C:\path\to\your\project\folder"

Then run:

docker build -t nec-sanction-screening:latest .
  • -t nec-sanction-screening:latest → gives the image a name and tag
  • The final . → means “use the current folder as the build context”
The first build takes longer because Docker downloads the .NET SDK and runtime base images. Subsequent builds are much faster thanks to layer caching.

When it finishes successfully, verify the image exists:

docker images

6. Run the container

Start the container with:

docker run --rm -p 8080:8080 --name nec-app nec-sanction-screening:latest
Flag Meaning
--rm Automatically remove the container when it stops
-p 8080:8080 Map host port 8080 → container port 8080
--name nec-app Give the container a friendly name
.NET 8 important change: Official ASP.NET Core container images now listen on port 8080 by default (not 80). Always map to 8080 unless you deliberately change the port with environment variables.

Open your browser and go to:

  • http://localhost:8080
  • If you have Swagger: http://localhost:8080/swagger

7. Problems we faced and how we fixed them

7.1 Singleton / Dependency Injection errors

Error: The application was complaining that services registered in Program.cs must be registered as Singleton (or lifetime mismatch errors appeared when the container started).

What happened:

Inside Docker the application runs in a different hosting model. Some services that worked fine on your local machine (especially ones registered as Scoped or Transient) started throwing lifetime validation errors.

How we fixed it:

  • Opened Program.cs
  • Checked every builder.Services.Add... registration
  • Changed the problematic services to AddSingleton where it made sense for the application
  • Rebuilt the image after the change
Example change: 
// Before (caused error)
builder.Services.AddScoped<IMyService, MyService>();

// After (fixed)
builder.Services.AddSingleton<IMyService, MyService>();

After fixing the registrations we ran the build command again:

docker build -t nec-sanction-screening:latest .

7.2 Adding a logs directory

Problem: The application tried to write log files but the folder did not exist inside the container → runtime crash or silent failure.

How we fixed it:

We added this line in the runtime stage of the Dockerfile (before copying the published files):

RUN mkdir -p /app/logs

This creates the /app/logs folder inside the final image so the application can write log files without permission or “directory not found” errors.

7.3 Hardcoding the environment in the Dockerfile

Problem: The application was not picking up the correct environment (Development / Production) when running inside the container.

How we fixed it:

We hardcoded the environment variables directly in the Dockerfile so the container always starts with the correct settings:

ENV ASPNETCORE_ENVIRONMENT=Production
ENV ASPNETCORE_URLS=http://+:8080
  • ASPNETCORE_ENVIRONMENT=Production → forces the app to run in Production mode
  • ASPNETCORE_URLS=http://+:8080 → makes Kestrel listen on all interfaces on port 8080 (required for Docker)
After adding the logs directory + environment variables and fixing the Singleton registrations, we rebuilt the image and the container started successfully.

9. Sharing the image with someone else

Option A – Push to Docker Hub (recommended)

  1. Create a free account on hub.docker.com
  2. Log in from the terminal: 
    docker login
  3. Tag the image with your Docker Hub username: 
    docker tag nec-sanction-screening:latest yourusername/nec-sanction-screening:latest
  4. Push it: 
    docker push yourusername/nec-sanction-screening:latest

The other person can then pull and run it:

docker pull yourusername/nec-sanction-screening:latest
docker run --rm -p 8080:8080 yourusername/nec-sanction-screening:latest

Option B – Save as a .tar file and send it

Save the image:

docker save nec-sanction-screening:latest -o nec-sanction-screening.tar

Send the .tar file. The other person loads it with:

docker load -i nec-sanction-screening.tar
docker run --rm -p 8080:8080 nec-sanction-screening:latest

10. Quick checklist

  1. Docker Desktop is installed and running (Linux containers mode)
  2. Dockerfile (no extension) exists next to the .csproj
  3. .dockerignore exists in the same folder
  4. Singleton / DI lifetime errors fixed in Program.cs
  5. Logs directory created with RUN mkdir -p /app/logs
  6. Environment variables hardcoded in the Dockerfile
  7. Built with docker build -t your-image-name:latest .
  8. Ran with -p 8080:8080
  9. App opens at http://localhost:8080

11. Optional easier method (no Dockerfile)

If you have the .NET 8 SDK installed, you can let the SDK create the image for you: 

dotnet publish -t:PublishContainer -c Release

This produces a local Docker image automatically. You can still use Docker Desktop to inspect, run, and export it.
